## ADR-001: Go вместо Node.js для Backend

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Нужен backend для LifeOS. Фронтенд на SvelteKit (Node.js). Варианты: Node.js (единый стек) или Go (отдельный бинарник).

**Решение:** Go 1.27.3 для backend. Node.js только для сборки фронтенда.

**Последствия:**
- ✅ Один статический бинарник для деплоя (нет Node.js runtime на Atom)
- ✅ Превосходная производительность на слабом железе (Atom D525)
- ✅ `modernc.org/sqlite` — pure Go SQLite без CGO
- ✅ Отличная конкурентность (goroutines) для SSE, Agent Runtime
- ✅ Сильная типизация, `sqlc`, `oapi-codegen`
- ❌ Два языка в проекте (Go + TypeScript)
- ❌ Нужна сборка фронтенда отдельно, затем embed в Go

**Альтернативы:**
- Node.js + Fastify/Express — отвергнуто: нужен Node.js runtime на Atom, хуже производительность, нет pure Go SQLite
- Rust — отвергнуто: кривая обучения, overkill для данного масштаба
- Python — отвергнуто: GIL, медленнее, нужен runtime

## ADR-002: SQLite вместо PostgreSQL

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Персональная система, один пользователь, локальные данные. Целевой сервер — Atom D525 с очень ограниченными ресурсами.

**Решение:** SQLite (`modernc.org/sqlite` v1.62.0, pure Go, без CGO).

**Последствия:**
- ✅ Zero-config, один файл, легко бэкапить (`.backup`)
- ✅ Нет отдельного процесса БД, нет потребления памяти под сервер
- ✅ Pure Go драйвер — работает на AMD64 v1 без CGO
- ✅ WAL mode даёт достаточную конкурентность для single-user
- ✅ `sqlc` + `goose` — типизированные запросы и миграции
- ❌ Нет встроенной репликации (не нужна)
- ❌ Ограниченная конкурентность записи (не проблема для single-user)
- ❌ Нет пользователей/прав (не нужны)

**Альтернативы:**
- PostgreSQL — отвергнуто: отдельный процесс, ~100MB RAM, сложнее деплой на Atom
- BoltDB/badger — отвергнуто: нет SQL, сложнее миграции, нет `sqlc`
- libSQL/Turso — отвергнуто: требует сеть, overkill

## ADR-003: Modular Monolith вместо микросервисов

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** LifeOS — персональная система. Один пользователь, один экземпляр. Микросервисы добавляют сложность без выгоды.

**Решение:** Один Go-процесс с внутренним модульным разделением (Domain, Application, Infrastructure, Transport, Agent).

**Последствия:**
- ✅ Простой деплой: один бинарник
- ✅ Нет сетевых вызовов между сервисами — ниже latency, выше надежность
- ✅ Транзакционность БД естественная
- ✅ Легко рефакторить (внутри процесса)
- ✅ Простое отладка и логирование
- ❌ Нет независимого масштабирования (не нужно)
- ❌ Нет изоляции сбоев (не критично для personal use)

**Альтернативы:**
- Микросервисы (API, Agent, MCP, DB отдельно) — отвергнуто: overkill, сложность деплоя на Atom
- Serverless — отвергнуто: vendor lock-in, холодный старт, не для локального Atom

## ADR-004: Собственный Agent Runtime вместо фреймворка

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Нужен LLM-ассистент с tool calling. Фреймворки (LangChain, LlamaIndex, AutoGen) тяжелые, навязывают свои абстракции.

**Решение:** Компактный Agent Runtime на Go (~500-1000 строк):
- Provider интерфейс (OpenRouter, Ollama)
- Tool registry с JSON Schema
- Контекст: задачи, входящие, время (Europe/Moscow)
- Выполнение инструментов → Application Services

**Последствия:**
- ✅ Полный контроль, нет vendor lock-in
- ✅ Инструменты = прямые вызовы Application Services (типобезопасно)
- ✅ Минимальные зависимости (`openai-go/v3` только для HTTP)
- ✅ Легко тестировать (моки Provider/Tools)
- ❌ Нужно самому реализовать: streaming, retries, token counting
- ❌ Нет встроенных цепочек/графов (пока не нужны)

**Альтернативы:**
- LangChain Go — отвергнуто: тяжелый, абстракции не под задачи
- Использовать OpenAI Assistants API — отвергнуто: vendor lock-in, нет локального Ollama
- Python-side agent — отвергнуто: нарушает single-binary, нужен Python runtime

## ADR-005: MCP как адаптер, а не отдельный сервер

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Model Context Protocol для интеграции с внешними клиентами (Claude Desktop, и т.д.). Вариант: отдельный MCP-сервер или встроенный адаптер.

**Решение:** MCP Adapter внутри LifeOS процесса (`internal/transport/mcp`). Streamable HTTP на `/mcp`. Инструменты MCP = те же Application Services, что и REST API.

**Последствия:**
- ✅ Единая бизнес-логика для REST, MCP, Agent
- ✅ Нет дублирования кода
- ✅ Один процесс, один порт (или path)
- ✅ Атомарность транзакций с REST API
- ❌ MCP клиент разделяет соединение с основным API (не критично)

**Альтернативы:**
- Отдельный MCP-сервер (Go/Node) — отвергнуто: дублирование логики, синхронизация схем
- MCP поверх SSE — отвергнуто: Streamable HTTP — современный стандарт

## ADR-006: Task Engine независим от LLM/Agent/MCP

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Архитектурный принцип: доменная логика задач не должна знать о существовании LLM.

**Решение:**
- Domain/Application не зависят от `internal/agent`, `internal/transport/mcp`, `internal/transport/http`
- Agent/MCP/HTTP вызывают Application Services
- LLM получает доступ к данным ТОЛЬКО через инструменты (tools)

**Последствия:**
- ✅ Task Engine тестируется без LLM, без сети
- ✅ Можно сменить провайдера LLM без изменений в домене
- ✅ Можно отключить Agent/MCP — Task Engine работает
- ✅ Чёткие границы ответственности

**Нарушения (запрещены):**
- `domain/task` импортирует `agent` или `mcp`
- `application/tasks` вызывает LLM напрямую
- LLM пишет в SQLite напрямую

## ADR-007: SvelteKit Static Adapter + embed

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Фронтенд на SvelteKit 2 + Svelte 5. Production не должен требовать Node.js сервер.

**Решение:** `@sveltejs/adapter-static` → статические файлы → `go:embed` в бинарник → Go отдаёт через HTTP.

**Последствия:**
- ✅ Production = один Go-бинарник, нет Node.js
- ✅ Vite dev server для разработки (HMR)
- ✅ PWA через `@vite-pwa/sveltekit`
- ✅ Type-safe API client через `openapi-typescript` + `openapi-fetch`
- ❌ Нет SSR (не нужно для SPA)
- ❌ Сборка в два этапа (npm run build → go build)

**Альтернативы:**
- SvelteKit Node adapter — отвергнуто: нужен Node.js на Atom
- Отдельный SPA (Vite + React/Vue) — отвергнуто: SvelteKit даёт routing, islands, лучше DX
- Go templates — отвергнуто: ухудшает DX, нет type-safety с API

## ADR-008: AMD64 v1 и CGO_DISABLED для Atom D525

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Целевой сервер — Intel Atom D525 (2010 г.). Поддерживает только базовый x86-64 (v1). Нет SSE4.1, SSE4.2, AVX, AES-NI.

**Решение:**
```bash
GOOS=linux GOARCH=amd64 GOAMD64=v1 CGO_ENABLED=0 go build
```

**Последствия:**
- ✅ Бинарик запускается на Atom D525
- ✅ `modernc.org/sqlite` — pure Go, работает без CGO
- ✅ Все Go-зависимости собираются под v1
- ❌ Нельзя использовать пакеты с ассемблером под v2/v3/v4
- ❌ Нельзя использовать CGO-зависимости (sqlite3, gtk, и т.д.)
- ⚠️ Нужно проверять каждую зависимость на совместимость

**Проверка:**
```bash
go tool objdump -s "TEXT" ./lifeos | grep -E "SSE4|AVX|AES" && echo "BAD" || echo "OK"
```

## ADR-009: Отказ от Docker на Atom

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Atom D525 — 2 ядра, 2-4 GB RAM. Docker добавляет overhead, сложность, потребление ресурсов.

**Решение:** Деплой напрямую через systemd. Бинарик + systemd unit + Tailscale Serve.

**Последствия:**
- ✅ Минимальный overhead (нет контейнерного runtime)
- ✅ Простые логи (journald)
- ✅ Простой откат (замена бинарника)
- ✅ Прямой доступ к файлам БД для бэкапа
- ❌ Нет изоляции файловой системы (не критично, single-user)
- ❌ Ручное управление зависимостями ОС (только libc)

**Альтернативы:**
- Docker + docker-compose — отвергнуто: overhead на Atom
- Podman — отвергнуто: тот же overhead
- Nix/Guix — отвергнуто: кривая обучения, overkill

## ADR-010: Server-Sent Events (SSE) вместо WebSocket

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Real-time обновления для фронтенда (новые задачи, изменения, сообщения ассистента). Нужно простое, надёжное решение.

**Решение:** SSE (`GET /api/v1/events`). Односторонний стрим сервер → клиент. Клиентские действия идут через REST.

**Последствия:**
- ✅ Проще WebSocket (HTTP/1.1 friendly, работает через прокси)
- ✅ Автоматическое переподключение браузером
- ✅ Работает через Tailscale Serve без дополнительной настройки
- ✅ `Last-Event-ID` для восстановления пропущенных
- ❌ Только сервер → клиент (клиент → сервер через REST — нормально)
- ❌ Лимит соединений на браузер (6 на хост, не проблема для single-tab app)

**Альтернативы:**
- WebSocket — отвергнуто: сложнее проксирование, нужен отдельный upgrade handler
- Polling — отвергнуто: лишняя нагрузка, задержка
- WebRTC — отвергнуто: overkill

## ADR-011: Даты и часовые пояса — строгая схема

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Баги с часовыми поясами — частая проблема. Нужен чёткий контракт.

**Решение:**
- `due_at` (timestamp with time zone) — UTC в БД, точный момент
- `due_date` / `planned_date` (date) — календарные даты, **без времени**, не конвертируются
- `timezone` на задаче — IANA TZ для интерпретации календарных дат
- Просроченность `due_date` = конец дня в TZ задачи

**Последствия:**
- ✅ Нет багов "задача просрочилась на час раньше/позже"
- ✅ Пользователь видит "10 ноября" — это 10 ноября в его TZ
- ✅ `due_at` для точных встреч, `due_date` для дедлайнов "к концу дня"
- ⚠️ Фронтенд должен правильно отображать оба типа

## ADR-016: Мутации ассистента требуют подтверждения

**Статус:** Accepted
**Дата:** 2026-11-12

**Контекст:** Ассистент получает инструменты, меняющие данные пользователя. Модель может ошибиться в аргументах или понять запрос неверно.

**Решение:** Инструменты делятся на read-only и мутирующие. Read-only выполняются сразу. Мутирующие создают `pending_action` с человекочитаемым превью; запись происходит только после `confirm`, а `reject` её отменяет. Подтверждение идемпотентно по статусу: повторное → `409`.

**Последствия:**
- ✅ Пользователь сохраняет контроль над изменениями
- ✅ Модель может объяснить, что именно будет сделано
- ✅ Аудит: pending action, результат и сообщения сохраняются
- ❌ Больше шагов в диалоге
- ❌ Модель должна корректно формулировать аргументы до подтверждения

## ADR-017: Проактивность без потока уведомлений

**Статус:** Accepted
**Дата:** 2026-11-12

**Контекст:** Проактивные подсказки полезны, но повторяющиеся уведомления быстро обесценивают систему.

**Решение:** Наблюдения вычисляются из актуальных данных, а не хранятся как лента. Пользователь может скрыть (`dismiss`) или отложить (`snooze`) конкретное наблюдение. Фоновый runner публикует событие только когда ключ появился впервые (или вернулся после исчезновения).

**Последствия:**
- ✅ Нет накопления устаревших уведомлений
- ✅ Наблюдение исчезает само, когда проблема решена
- ✅ Пользователь управляет шумом
- ❌ Нет истории наблюдений (при необходимости добавим отдельно)

## ADR-018: Достоверность вывода — по числу независимых источников

**Статус:** Accepted
**Дата:** 2026-04-12

**Контекст:** Исследование в интернете даёт текст, а не знание. Один сайт может
ошибаться, устареть или быть пересказом другого; модель, пересказывающая
найденное, легко смешивает увиденное с собственным выводом.

**Решение:** Уровень достоверности определяется детерминированно, без участия
модели. Утверждение считается `fact` только если его подтверждают минимум два
разных сайта (совпадение по значимым словам с учётом словоформ, а не по точной
формулировке). Утверждение одного источника — `assumption`. Отдельно
фиксируется расхождение: если два похожих утверждения по-разному отрицают общее
слово или приводят разные числа, оба получают `conflict` и перестают быть
фактом. Недоступная страница даёт не «источник», а поисковую выдержку с низким
доверием и явной пометкой «страница не прочитана». Итог отчёта пишется
шаблоном, поэтому не может сказать больше, чем показали источники.

**Последствия:**
- ✅ Факт и предположение не смешиваются, и это проверяемо, а не «на усмотрение модели»
- ✅ Отчёт воспроизводим: те же страницы дают тот же результат
- ✅ Пользователь видит, где источники спорят, а не сглаженный ответ
- ❌ Формулировки, пересказанные разными словами, могут не подтвердить друг друга: такой вывод останется предположением, хотя мог быть верным
- ❌ Порог совпадения — эвристика; при необходимости его придётся калибровать

## ADR-019: Внешний сервис — источник с разрешением, а не второе хранилище

**Статус:** Accepted
**Дата:** 2026-04-12

**Контекст:** Подключение к внешним API, MCP-серверам и скриптам даёт LifeOS
возможности, но и открывает два риска: система начинает зависеть от чужого
сервиса и получает право менять что-то вовне без ведома пользователя.

**Решение:** Собственная база LifeOS остаётся основой; внешний сервис — источник
с явным разрешением. У каждого подключения есть режим (`read`, `write`, `sync`),
доверие и адрес; режим проверяется перед каждым обращением, а отказ попадает в
журнал. Ассистент подключает источник только выключенным и только на чтение;
включение и расширение прав — действие пользователя в разделе «Исследования».
Источник-скрипт создаёт только пользователь, и он всегда работает на чтение:
запуск без оболочки, ввод подставляется одним аргументом. Обращения к внешнему
сервису внутри автоматизации запрещены: расписание — не согласие на отправку
изменений.

**Последствия:**
- ✅ Ни один внешний сервис не становится обязательным местом хранения данных
- ✅ Разрешение видно и отзывается в одном месте
- ✅ Журнал обращений отвечает на вопрос «что LifeOS делала с этим сервисом», даже после его удаления
- ❌ Нет готового каталога интеграций и OAuth: каждый источник пользователь описывает сам
- ❌ Автоматизация не может использовать внешний API как шаг; для этого нужен отдельный согласованный сценарий

## ADR-020: Совпадение утверждений — по названным значениям, а не только по словам

**Статус:** Accepted
**Дата:** 2026-11-17
**Уточняет:** ADR-018

**Контекст:** Первая версия сравнения считала утверждения одним и тем же, если
совпадала доля значимых слов. «OpenAI основан Сэмом Альтманом» и «OpenAI основан
Илоном Маском» делят половину слов, и оба утверждения попадали в один вывод с
двумя ссылками — то есть в факт, которого не утверждает ни один источник.

**Решение:** Утверждения сливаются только при совпадении значимых слов **и**
названных значений: имён, организаций, годов, сумм, версий. Значения извлекаются
из исходного текста (заглавные слова, числа), сравниваются по точному значению
для чисел и по основе для слов. Если обе стороны называют разные значения в одной
роли, это расхождение: оно показывается с цитатой второй стороны и никогда не
становится фактом. Если значения добавляет только одна сторона («в Go 1.24
релиз…» против «релиз…»), это всё то же утверждение с подробностью.
Независимость подтверждения считается по регистрируемому домену, а факт требует
хотя бы одной действительно прочитанной страницы.

**Последствия:**
- ✅ Противоположные утверждения больше не могут превратиться в факт
- ✅ Перепечатка под другим поддоменом того же издателя не считается вторым сайтом
- ✅ Две поисковые выдержки не дают факта: зацепка — не подтверждение
- ❌ Строгость снижает число фактов: пересказ того же самого другими словами с
  другим набором имён останется предположением
- ❌ Разные значения, разнесённые по длинным предложениям, могут не распознаться
  как замена — тогда два вывода просто останутся рядом, без ложного факта

## ADR-021: Действия вовне — журнал до вызова, сетевая политика одна на всё исходящее

**Статус:** Accepted
**Дата:** 2026-11-17

**Контекст:** Две разные опасности одного модуля. Изменяющий вызов внешнего
сервиса мог пройти, а журнал — не записаться: тогда LifeOS не знает, что
изменила. И чтение страниц принимало любой адрес, включая локальные сервисы и
облачные metadata-эндпоинты: адрес приходит из поисковой выдачи и от модели, а
не от пользователя.

**Решение:** Каждое обращение журналируется **до** отправки: строка создаётся со
статусом `started` и закрывается исходом (`ok`, `refused`, `failed`) — обещание
фиксировать каждый контакт нельзя держать задним числом. Если запись в журнал не
удалась, изменяющий вызов не выполняется (`503`), а чтение идёт с
предупреждением: чтение ничего не меняет. После перезапуска незакрытая строка
становится `unknown` — сервис мог принять запрос, и это честнее, чем молчание. Для MCP «изменяет ли операция что-то» определяется не HTTP-методом, а
аннотацией инструмента от самого сервера: без заявленного намерения записи
вызывается только инструмент с `readOnlyHint`, инструмент без аннотации считается
изменяющим.

Сетевая политика одна на всё исходящее: чтение страниц, поисковый запрос и
вызовы источников идут через один guard. Адрес проверяется перед соединением и
на каждом редиректе — HTTP API и MCP отвечают через HTTP, и их редирект на
внутренний адрес закрыт так же, как у страниц, — а dial идёт на уже
проверенный IP: иначе второе разрешение имени оставляло бы окно для DNS
rebinding. Loopback, приватные, link-local, CGNAT и служебные адреса
(169.254.169.254, 100.100.100.200, 192.0.0.192, fd00:ec2::254) запрещены.
Адрес подключённого источника — выбор пользователя, поэтому его хост может жить
в его сети, но только этот хост: редирект на другую машину внутренней сети —
уже не его источник, а служебные адреса запрещены в любой политике. Вывод
команды источника ограничивается во время выполнения: при превышении команда
останавливается, а не буферизуется целиком.

**Последствия:**
- ✅ Нет обращения вовне без записи о нём; неизвестный исход назван явно
- ✅ Модель не может прочитать локальный сервис или metadata-эндпоинт — ни
  напрямую, ни редиректом подключённого источника
- ✅ Скрипт источника не может исчерпать память процесса своим выводом
- ❌ Проверка адреса требует разрешения имени на каждый запрос: медленнее, чем
  общий HTTP-клиент
- ❌ Каждый вызов требует двух записей журнала вместо одной

## ADR-022: Чтение через MCP — разрешает пользователь, а не сервер сам о себе

**Статус:** Accepted
**Дата:** 2026-11-18

**Контекст:** Аннотация `readOnlyHint` из спецификации MCP — это заявление
сервера о своих инструментах. Она не проверяется и не проверяема: сервер,
назвавший свою операцию удаления «только чтением», убеждает LifeOS выполнить её
без изменения данных. Доверять ей как гарантии — значит разрешить удалённому
сервису определять собственные права.

**Решение:** Без заявленного намерения записи инструмент MCP выполняется только
при двух условиях сразу: пользователь включил его по имени в список
`allowed_tools` источника, **и** сервер пометил его `readOnlyHint: true`.
Список заполняет только пользователь (интерфейс источника); ассистент его не
создаёт и не меняет — так же, как скрипты. Инструмент вне списка, без пометки
или неизвестный серверу отклоняется и попадает в журнал как отказ. С
намерением записи (`write: true`) инструмент идёт через режим `write`/`sync`
и подтверждение пользователя — как и любой другой изменяющий вызов.
В интерфейсе и документации пометка сервера никогда не называется гарантией.

**Последствия:**
- ✅ Сервер не может сам себе выдать права: без записи пользователя ничего не
  выполняется
- ✅ Решение явное и реверсируемое: список виден и правится в карточке источника
- ❌ Честный сервер тоже требует ручной настройки списка — плата за то, что
  решение остаётся за человеком
- ❌ Запись в список — это доверие именно этому инструменту; LifeOS не
  проверяет, что сервер не изменил его поведение позже

## ADR-023: Подстановка значений определяется по форме предложения

**Статус:** Accepted
**Дата:** 2026-11-18
**Уточняет:** ADR-020

**Контекст:** ADR-020 различает замену значения и лишнюю подробность по
названным значениям — заглавным словам и числам. Но имена пишут и строчными:
пост форума, расшифровка, сгенерированная страница дают «founded by sam altman»
против «founded by elon musk», где обе стороны делят почти все слова, различие
нигде не «значение» с точки зрения регистра, и утверждения снова сливались бы в
ложный факт.

**Решение:** Смотреть на форму предложения, а не на регистр. Одно утверждение
переходит в другое только добавлением и выбрасыванием слов (выравнивание по
совпадающим словам). Если на одном месте фразы стоят два разных слова —
«founded by **sam altman**» против «founded by **elon musk**», «grafana cloud»
против «datadog», «200 миллисекунд» против «400» — это подстановка значения в
любом регистре: утверждения не сливаются и получают расхождение с цитатой
второй стороны. Разбросанные односторонние добавки («In Go 1.24 the language
adds…» против «The release adds…») остаются подробностями: они не образуют пары
на одном месте.

**Уточнение (словоформы, не общее начало).** Слова считаются одним значением,
только если одно — словоформа другого: от основы отходит короткое окончание
(«сэм»/«сэма», "supports"/"supported", «альтман»/«альтмана»). Общее начало —
не признак: «John» и «Johnson» делят его и остаются разными людьми, «Anna» и
«Annabelle» — разными именами, а «founded» и «founder» — разными словами,
которые общее начало притворяло бы одним якорем выравнивания. Ложный якорь в
середине подставленного места позволял обойти его двумя сдвинутыми пропусками:
«…founded by **sam altman** said the company…» и «…founded by **elon musk**
said the company…» сходились в одно утверждение. С производными окончаниями
осторожно: «runner»/«runs» — разные слова, и это безопасный исход.

**Последствия:**
- ✅ Ложный факт невозможен и для строчных имён, и для смешанного написания
- ✅ Словоформы и падежи одного имени не притворяются подстановкой
- ✅ Похожие имена (John/Johnson, Anna/Annabelle) не сливаются даже в длинных
  одинаковых фразах
- ❌ «Runner»/«runs» — уже разные слова (словообразование, а не словоформа):
  утверждения останутся отдельными предположениями — и это безопасный исход
- ❌ Полностью переписанное утверждение с подстановкой в середине может не
  распознаться как расхождение и останется двумя отдельными предположениями

## ADR-024: Имя не решает: адрес закрепляется проверкой

**Статус:** Accepted
**Дата:** 2026-11-18
**Уточняет:** ADR-021

**Контекст:** Проверка адреса и соединение — два разных разрешения имени. Если
проверка разрешает `api.example.com` в публичный адрес, а к моменту соединения
DNS отвечает `127.0.0.1`, правило «локальное можно только своему хосту»
пропускает соединение: хост-то тот самый. DNS rebinding работает именно на
этой щели — разрешение привязано к имени, а не к проверенному адресу.

**Решение:** Проверка **закрепляет адреса** (`pinEndpoint`): соединение может
уйти только на адрес из проверенного ответа. Локальный адрес допускается, лишь
если был в этом ответе — пользователь, указавший свой сервер в своей сети,
получает его же; имя, сменившее ответ на локальный после проверки, получает
отказ («адрес изменился после проверки»). Публичный адрес может смениться на
публичный: за этим не стоит путь во внутреннюю сеть, а гео-балансировка DNS
честных сервисов продолжает работать. Встроенный поиск — конфигурация, а не
подключённый источник: по умолчанию он идёт как публичный трафик, и локальный
поисковый сервер включается отдельной настройкой
(`LIFEOS_ALLOW_LOCAL_SEARCH`), а не безусловным доверием к его имени.

**Последствия:**
- ✅ DNS rebinding закрыт для страниц, поиска, HTTP API и MCP — везде, где имя
  разрешается повторно
- ✅ Свой локальный источник и локальный поиск (с настройкой) продолжают
  работать
- ❌ Имя, честно сменившее один локальный адрес на другой внутри запроса, будет
  отклонено — редкий и безопасный отказ
- ❌ Ещё одно разрешение имени на запрос: проверка и соединение разрешают имя
  по отдельности
