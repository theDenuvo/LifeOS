## ADR-001: Go вместо Node.js для Backend

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Нужен backend для LifeOS. Фронтенд на SvelteKit (Node.js). Варианты: Node.js (единый стек) или Go (отдельный бинарник).

**Решение:** Go 1.27.3 для backend. Node.js только для сборки фронтенда.

**Последствия:**
- ✅ Один статический бинарник для деплоя (нет Node.js runtime на Atom)
- ✅ Превосходная производительность на слабом железе (Atom D525)
- ✅ `modernc.org/sqlite` — pure Go SQLite без CGO
- ✅ Отличная конкурентность (goroutines) для SSE, Agent Runtime
- ✅ Сильная типизация, `sqlc`, `oapi-codegen`
- ❌ Два языка в проекте (Go + TypeScript)
- ❌ Нужна сборка фронтенда отдельно, затем embed в Go

**Альтернативы:**
- Node.js + Fastify/Express — отвергнуто: нужен Node.js runtime на Atom, хуже производительность, нет pure Go SQLite
- Rust — отвергнуто: кривая обучения, overkill для данного масштаба
- Python — отвергнуто: GIL, медленнее, нужен runtime

## ADR-002: SQLite вместо PostgreSQL

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Персональная система, один пользователь, локальные данные. Целевой сервер — Atom D525 с очень ограниченными ресурсами.

**Решение:** SQLite (`modernc.org/sqlite` v1.62.0, pure Go, без CGO).

**Последствия:**
- ✅ Zero-config, один файл, легко бэкапить (`.backup`)
- ✅ Нет отдельного процесса БД, нет потребления памяти под сервер
- ✅ Pure Go драйвер — работает на AMD64 v1 без CGO
- ✅ WAL mode даёт достаточную конкурентность для single-user
- ✅ `sqlc` + `goose` — типизированные запросы и миграции
- ❌ Нет встроенной репликации (не нужна)
- ❌ Ограниченная конкурентность записи (не проблема для single-user)
- ❌ Нет пользователей/прав (не нужны)

**Альтернативы:**
- PostgreSQL — отвергнуто: отдельный процесс, ~100MB RAM, сложнее деплой на Atom
- BoltDB/badger — отвергнуто: нет SQL, сложнее миграции, нет `sqlc`
- libSQL/Turso — отвергнуто: требует сеть, overkill

## ADR-003: Modular Monolith вместо микросервисов

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** LifeOS — персональная система. Один пользователь, один экземпляр. Микросервисы добавляют сложность без выгоды.

**Решение:** Один Go-процесс с внутренним модульным разделением (Domain, Application, Infrastructure, Transport, Agent).

**Последствия:**
- ✅ Простой деплой: один бинарник
- ✅ Нет сетевых вызовов между сервисами — ниже latency, выше надежность
- ✅ Транзакционность БД естественная
- ✅ Легко рефакторить (внутри процесса)
- ✅ Простое отладка и логирование
- ❌ Нет независимого масштабирования (не нужно)
- ❌ Нет изоляции сбоев (не критично для personal use)

**Альтернативы:**
- Микросервисы (API, Agent, MCP, DB отдельно) — отвергнуто: overkill, сложность деплоя на Atom
- Serverless — отвергнуто: vendor lock-in, холодный старт, не для локального Atom

## ADR-004: Собственный Agent Runtime вместо фреймворка

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Нужен LLM-ассистент с tool calling. Фреймворки (LangChain, LlamaIndex, AutoGen) тяжелые, навязывают свои абстракции.

**Решение:** Компактный Agent Runtime на Go (~500-1000 строк):
- Provider интерфейс (OpenRouter, Ollama)
- Tool registry с JSON Schema
- Контекст: задачи, входящие, время (Europe/Moscow)
- Выполнение инструментов → Application Services

**Последствия:**
- ✅ Полный контроль, нет vendor lock-in
- ✅ Инструменты = прямые вызовы Application Services (типобезопасно)
- ✅ Минимальные зависимости (`openai-go/v3` только для HTTP)
- ✅ Легко тестировать (моки Provider/Tools)
- ❌ Нужно самому реализовать: streaming, retries, token counting
- ❌ Нет встроенных цепочек/графов (пока не нужны)

**Альтернативы:**
- LangChain Go — отвергнуто: тяжелый, абстракции не под задачи
- Использовать OpenAI Assistants API — отвергнуто: vendor lock-in, нет локального Ollama
- Python-side agent — отвергнуто: нарушает single-binary, нужен Python runtime

## ADR-005: MCP как адаптер, а не отдельный сервер

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Model Context Protocol для интеграции с внешними клиентами (Claude Desktop, и т.д.). Вариант: отдельный MCP-сервер или встроенный адаптер.

**Решение:** MCP Adapter внутри LifeOS процесса (`internal/transport/mcp`). Streamable HTTP на `/mcp`. Инструменты MCP = те же Application Services, что и REST API.

**Последствия:**
- ✅ Единая бизнес-логика для REST, MCP, Agent
- ✅ Нет дублирования кода
- ✅ Один процесс, один порт (или path)
- ✅ Атомарность транзакций с REST API
- ❌ MCP клиент разделяет соединение с основным API (не критично)

**Альтернативы:**
- Отдельный MCP-сервер (Go/Node) — отвергнуто: дублирование логики, синхронизация схем
- MCP поверх SSE — отвергнуто: Streamable HTTP — современный стандарт

## ADR-006: Task Engine независим от LLM/Agent/MCP

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Архитектурный принцип: доменная логика задач не должна знать о существовании LLM.

**Решение:**
- Domain/Application не зависят от `internal/agent`, `internal/transport/mcp`, `internal/transport/http`
- Agent/MCP/HTTP вызывают Application Services
- LLM получает доступ к данным ТОЛЬКО через инструменты (tools)

**Последствия:**
- ✅ Task Engine тестируется без LLM, без сети
- ✅ Можно сменить провайдера LLM без изменений в домене
- ✅ Можно отключить Agent/MCP — Task Engine работает
- ✅ Чёткие границы ответственности

**Нарушения (запрещены):**
- `domain/task` импортирует `agent` или `mcp`
- `application/tasks` вызывает LLM напрямую
- LLM пишет в SQLite напрямую

## ADR-007: SvelteKit Static Adapter + embed

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Фронтенд на SvelteKit 2 + Svelte 5. Production не должен требовать Node.js сервер.

**Решение:** `@sveltejs/adapter-static` → статические файлы → `go:embed` в бинарник → Go отдаёт через HTTP.

**Последствия:**
- ✅ Production = один Go-бинарник, нет Node.js
- ✅ Vite dev server для разработки (HMR)
- ✅ PWA через `@vite-pwa/sveltekit`
- ✅ Type-safe API client через `openapi-typescript` + `openapi-fetch`
- ❌ Нет SSR (не нужно для SPA)
- ❌ Сборка в два этапа (npm run build → go build)

**Альтернативы:**
- SvelteKit Node adapter — отвергнуто: нужен Node.js на Atom
- Отдельный SPA (Vite + React/Vue) — отвергнуто: SvelteKit даёт routing, islands, лучше DX
- Go templates — отвергнуто: ухудшает DX, нет type-safety с API

## ADR-008: AMD64 v1 и CGO_DISABLED для Atom D525

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Целевой сервер — Intel Atom D525 (2010 г.). Поддерживает только базовый x86-64 (v1). Нет SSE4.1, SSE4.2, AVX, AES-NI.

**Решение:**
```bash
GOOS=linux GOARCH=amd64 GOAMD64=v1 CGO_ENABLED=0 go build
```

**Последствия:**
- ✅ Бинарик запускается на Atom D525
- ✅ `modernc.org/sqlite` — pure Go, работает без CGO
- ✅ Все Go-зависимости собираются под v1
- ❌ Нельзя использовать пакеты с ассемблером под v2/v3/v4
- ❌ Нельзя использовать CGO-зависимости (sqlite3, gtk, и т.д.)
- ⚠️ Нужно проверять каждую зависимость на совместимость

**Проверка:**
```bash
go tool objdump -s "TEXT" ./lifeos | grep -E "SSE4|AVX|AES" && echo "BAD" || echo "OK"
```

## ADR-009: Отказ от Docker на Atom

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Atom D525 — 2 ядра, 2-4 GB RAM. Docker добавляет overhead, сложность, потребление ресурсов.

**Решение:** Деплой напрямую через systemd. Бинарик + systemd unit + Tailscale Serve.

**Последствия:**
- ✅ Минимальный overhead (нет контейнерного runtime)
- ✅ Простые логи (journald)
- ✅ Простой откат (замена бинарника)
- ✅ Прямой доступ к файлам БД для бэкапа
- ❌ Нет изоляции файловой системы (не критично, single-user)
- ❌ Ручное управление зависимостями ОС (только libc)

**Альтернативы:**
- Docker + docker-compose — отвергнуто: overhead на Atom
- Podman — отвергнуто: тот же overhead
- Nix/Guix — отвергнуто: кривая обучения, overkill

## ADR-010: Server-Sent Events (SSE) вместо WebSocket

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Real-time обновления для фронтенда (новые задачи, изменения, сообщения ассистента). Нужно простое, надёжное решение.

**Решение:** SSE (`GET /api/v1/events`). Односторонний стрим сервер → клиент. Клиентские действия идут через REST.

**Последствия:**
- ✅ Проще WebSocket (HTTP/1.1 friendly, работает через прокси)
- ✅ Автоматическое переподключение браузером
- ✅ Работает через Tailscale Serve без дополнительной настройки
- ✅ `Last-Event-ID` для восстановления пропущенных
- ❌ Только сервер → клиент (клиент → сервер через REST — нормально)
- ❌ Лимит соединений на браузер (6 на хост, не проблема для single-tab app)

**Альтернативы:**
- WebSocket — отвергнуто: сложнее проксирование, нужен отдельный upgrade handler
- Polling — отвергнуто: лишняя нагрузка, задержка
- WebRTC — отвергнуто: overkill

## ADR-011: Даты и часовые пояса — строгая схема

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Баги с часовыми поясами — частая проблема. Нужен чёткий контракт.

**Решение:**
- `due_at` (timestamp with time zone) — UTC в БД, точный момент
- `due_date` / `planned_date` (date) — календарные даты, **без времени**, не конвертируются
- `timezone` на задаче — IANA TZ для интерпретации календарных дат
- Просроченность `due_date` = конец дня в TZ задачи

**Последствия:**
- ✅ Нет багов "задача просрочилась на час раньше/позже"
- ✅ Пользователь видит "10 ноября" — это 10 ноября в его TZ
- ✅ `due_at` для точных встреч, `due_date` для дедлайнов "к концу дня"
- ⚠️ Фронтенд должен правильно отображать оба типа

## ADR-012: XSS-защита — только textContent/createElement

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Фронтенд рендерит пользовательские данные (задачи, заметки, сообщения ассистента).

**Решение:** Никакого `innerHTML`, `dangerouslySetInnerHTML`, `v-html`. Только `textContent`, `createElement`, Svelte `{@html}` запрещён для пользовательского контента.

**Последствия:**
- ✅ Полная защита от XSS
- ✅ Простая аудиторская проверка
- ⚠️ Нет rich text в задачах (plain text + markdown rendering через безопасный парсер если понадобится)

## ADR-013: Ошибки — application/problem+json

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Единый формат ошибок для REST API, понятный фронтенду и клиентам MCP.

**Решение:** RFC 9457 (Problem Details). Все ошибки возвращают `application/problem+json`.

**Последствия:**
- ✅ Стандартизированный формат
- ✅ Машиночитаемые коды ошибок (`type`, `errors[].code`)
- ✅ Фронтенд может показывать локализованные сообщения по кодам

## ADR-014: Идемпотентность через Idempotency-Key

**Статус:** Accepted
**Дата:** 2026-11-10

**Контекст:** Сетевые ошибки, повторные запросы от фронтенда/ассистента.

**Решение:** `POST /api/v1/tasks` и `POST /api/v1/inbox` принимают `Idempotency-Key` (UUID), сохраняют результат 24ч.

- ✅ Безопасные ретраи

## ADR-016: Мутации ассистента требуют подтверждения

**Статус:** Accepted
**Дата:** 2026-11-12

**Контекст:** Ассистент получает инструменты, меняющие данные пользователя. Модель может ошибиться в аргументах или понять запрос неверно.

**Решение:** Инструменты делятся на read-only и мутирующие. Read-only выполняются сразу. Мутирующие создают `pending_action` с человекочитаемым превью; запись происходит только после `confirm`, а `reject` её отменяет. Подтверждение идемпотентно по статусу: повторное → `409`.

**Последствия:**
- ✅ Пользователь сохраняет контроль над изменениями
- ✅ Модель может объяснить, что именно будет сделано
- ✅ Аудит: pending action, результат и сообщения сохраняются
- ❌ Больше шагов в диалоге
- ❌ Модель должна корректно формулировать аргументы до подтверждения

## Как добавлять новые решения

1. Создайте новый ADR с следующим номером
2. Заполните все поля формата
3. Укажите статус `Proposed` → обсуждение → `Accepted`/`Rejected`
4. Если отменяет предыдущее — пометьте старое `Superseded` с ссылкой на новый
5. Никогда не удаляйте ADR
